# axum as a second framework: one seam, the same wire answers

Date: 2026-10-26 (imported) · Status: accepted upstream, imported; **superseded in part** in this workspace (see below)

Formerly rok-sqlc ADR 0019 (rok-sqlc 0.7.0). Imported under workspace ADR 0016. The text is upstream's. The terms are this workspace's: the `rok sqlc` front door, `rok.toml`, and engine ADR numbers after the import.

> **Superseded in this workspace.** This workspace grew its own axum support before the import (engine ADR 0016 as amended, and the engine's `generator/api/framework.rs`). Where the two decided the same question differently, the workspace's decision stands (workspace ADR 0016):
>
> - **A1, the spelling.** The key's values are `actix_web` (the default) and `axum`, not `actix`. `rok sqlc init` takes `-w/--api-framework`, not `-f/--framework`. The rest of A1 holds: one framework per project, and its extractor checked rather than inferred.
> - **A3, how handlers reach services.** A generated axum handler takes its service as `Extension<Arc<XService>>`, and the root's `generated.rs` holds one `router(pool)`. There is no `Services`/`FromRef`/`AppState` wiring in generated code. A template's hand-written features may hold their state however the template decides.
> - **A7, the fixtures.** The axum fixture is `crates/rok-data-sqlc/tests/axum-app`, generated by rok-cli's `fixture_compile` suite and gated there (lint, rustfmt, `check-arch`, its tests). There is no `tests/api-app-axum` and no shared `tests/api-suite/`. `check-arch`'s rule 1 already names the project's framework crate (engine ADR 0016's amendment).
>
> The following are ported only where the workspace lacks them:
>
> - the reworded `Path`/`Query` rejections (A2's wire answers);
> - the templates' middleware (A4);
> - the template drift test (A6);
> - the versions (A8).
>
> A5 (no `utoipa-axum`) already holds here.

Until rok-sqlc 0.7.0, the engine generated API features only for actix-web, and `init --template axum` answered "unknown template". Engine ADR 0016 promised axum as a second framework against the same contract, and that contract comes from an axum starter. In 0.7.0:

- a project picks its framework;
- the generator emits that framework's HTTP edge over code that is otherwise identical;
- `templates/axum-api/` mirrors the actix template, account flows included.

The decisions are A1–A8 of `.scratch/rok-sqlc-0-7/notes/axum-decisions.md` (in the rok-sqlc repository). The guide covers both frameworks where they differ.

**A project picks one framework (A1).**

- **The key:** `[api] framework = "actix" | "axum"`, `actix` by default, so a 0.6 project generates what it did.
- **Scaffolding:** `rok sqlc init -f/--framework axum` scaffolds the axum skeleton, and `init --template axum` copies the axum template. `--framework` and `--template` don't combine, since a template has its framework.
- **Extractors are checked, not inferred:** the API needs its framework's extractor in `extractors` (`actix_web` or `axum`). `framework = "axum"` with only `actix_web` stops `g`, naming what is missing. Inferring the framework from the extractors would let a data-layer setting decide the API's shape: the setting only says which extractors `db/http/` emits, and that may be both.

**Only the HTTP edge differs (A2).**

- **Per framework:** `routes.rs`, `handlers.rs`, the request extractors (`AuthUser`, `AdminUser`, `Tenant`, `ValidatedJson`, `Path`, `Query`, `IfMatch`), the `AppError`-to-response mapping, and the server setup in `main.rs` and `app.rs`.
- **The same for both:** `dto.rs`, `model.rs`, `repo.rs`, `service_api.rs`, `service.rs` (ports included), the data layer, and the `#[utoipa::path]` annotations. So the OpenAPI document is byte-identical apart from its title.
- **The seam in the generator** is one type, `ApiFramework`. It answers each piece a handler renderer asks for: how a handler takes its service, its path and its query, what it returns, and how it answers. It also holds the framework's descriptors: its crate's name, the other framework, the wiring `generated.rs` hands `app.rs`, the Swagger UI feature, and the skeleton files.
- **Rendering:** files whose code differs whole (`routes.rs`, `generated.rs`, `shared/health.rs`, `tenant.rs` and the head of `validation.rs`) are rendered by a function per framework. The rest is rendered once.

**Handlers reach services through `State` and `FromRef` (A3).**

- **The generated wiring:** `features/generated.rs` declares `Services`, one `Arc<XService>` per feature, built once by `register_services(&pool)`. It implements `FromRef<Services>` and `FromRef<AppState>` for each `Arc<XService>`.
- **The scaffolded state:** the user-owned `AppState` derives `FromRef` and holds `services: Services`, the pool and the auth keys.
- **Handlers and routers:** a generated handler takes `State(service): State<Arc<UsersService>>`, and a generated router is `Router<AppState>`.
- **Hand-written features:** a hand-written feature adds its service as an `AppState` field, built once in `AppState::new`, never per request. The axum template's `auth` and `account` are fields, and a test swaps the breach check or the audit trail with `AppState::with_breach` and `with_audit`.
- **Alternatives:** one extension per service is untyped (a missing one is a runtime `500`), and a generic `AppState<S>` makes every signature name it. `FromRef` keeps the handler's dependency in its type and needs no generics.

**Middleware is tower-http, plus two small pieces of our own (A4).**

- **The stack:** the axum skeleton and template apply tracing, CORS (same-origin), request ids (`x-request-id`, set and propagated), a 2 MiB body limit (`413`), and a 30-second request timeout.
- **The timeout:** `app::time_out`, an axum middleware over `tokio::time::timeout`. tower-http's `TimeoutLayer` answers a `408` with an empty body; ours answers `408 request_timeout` with the wire standard's body, like every other error.
- **The `/auth` rate limit:** the template's own tower `Layer` over `governor`'s keyed GCRA (MIT), with the same `429` and `Retry-After` as actix's middleware. `tower_governor` was not used, as its answers and key extraction aren't ours.
- **Shared limiter code:** the limiter's count and `client_ip` live in `shared/rate_limit/limiter.rs`, byte-identical in both templates. `rate_limit/mod.rs` is the framework's middleware.
- **The peer:** it comes from `ConnectInfo`, which `app::serve` provides through `into_make_service_with_connect_info`. A router served without it counts every client as `0.0.0.0`, so the first such request logs a warning.

**Every request under `/api/v1/auth` counts.**

- actix wraps the whole `/api/v1/auth` scope in the limit.
- axum nests the auth routes under `/api/v1/auth` behind the same limit, with a fallback and a method-not-allowed fallback. So an unknown path or method there is counted and answers the wire standard's `404`.
- The actix scope's default service gives the same `404` body.
- `/api/v1/auth/me` (the `account` feature's) is its own route behind the same limiter in both.

**What still differs on the wire.** The answers are the same, statuses, codes and messages included:

- axum's `Path` and `Query` rejections are reworded to actix-web's (`Path deserialize error: can not parse "abc" to a i64`).
- A path rejection that is a wiring bug (a route without the parameters its handler takes) is a `500 internal_error`, with its detail logged.

What the frameworks add around those answers differs, and is documented rather than hidden:

- Only axum answers `408 request_timeout`. actix-web has no request timeout; put one in your proxy.
- Only axum sets `x-request-id`.
- Outside `/api/v1/auth`, an unknown route is an empty `404` in both. But a wrong method on a known path is axum's empty `405` and actix-web's empty `404`.

**OpenAPI: the same annotations, no `utoipa-axum` (A5).** The handlers keep `#[utoipa::path]`, and the derived `OpenApi` lists them, exactly as for actix. Swagger UI comes from `utoipa-swagger-ui`'s `axum` feature. `utoipa-axum`'s `OpenApiRouter` would derive the paths from the routes, but only for axum. The two frameworks' documents would then be built two ways and could drift, and the document test already compares both against one expected file.

**The axum template mirrors the actix one, checked by a drift test (A6).**

- **Same contract:** `templates/axum-api/` is generated from the same `schema.sql`, passes the same contract test against the same OpenAPI document, and has all of M5's account flows.
- **Copies, not a shared crate:** each template stays self-contained, since a user copies one. So the shared code is copied.
- **The drift test:** `tests/template_drift.rs` fails when a framework-independent file differs between the templates. Those files are:
  - `migrations/` and `queries/`;
  - `src/shared/security/`, `src/shared/mail/` and `src/shared/rate_limit/limiter.rs`;
  - the generated features' `dto.rs`, `model.rs`, `repo.rs`, `service.rs` and `service_api.rs`;
  - the hand-written `auth` and `account` features' `dto.rs` and `service.rs`.
- **Changes to the actix template:** making those copies identical moved two things. Password hashing runs on `tokio::task::spawn_blocking` (not `actix_web::web::block`), which needs tokio's `rt` feature. And `AuthService` derives `Clone`.

**Generator tests and `check-arch` know the framework (A7).**

- **Fixtures:** `tests/api-app-axum` is generated from `tests/api-app`'s migrations with `framework = "axum"`. Both fixtures run the same suites (`tests/api-suite/`), each through a small adapter that sends a request its framework's way. They assert the same wire answers and the same OpenAPI document.
- **`check-arch`:** rule 1 names the project's framework crate (`actix_web` or `axum`). The other framework's crate is a `rule-1` violation everywhere but the data layer, whose `extractors` may serve both. For example: ``src/features/notes/service.rs:32: rule-1: `actix_web::HttpResponse`: the project uses axum (`[api] framework`), so nothing but db/ may use actix_web``.

**Versions (A8).**

- axum 0.8, tower-http 0.6, and tokio with `rt-multi-thread`, `macros`, `signal`, `net` and `time`.
- The server stops with `axum::serve(...).with_graceful_shutdown`.
- The template's mail sender runs under `tokio::spawn`, and the same signal stops it after the requests in flight finish.

## Considered Options

- **A trait over frameworks in the generated code** (one handler body, an adapter per framework). Rejected: generated code would gain an abstraction users must learn. Each framework's idioms (`web::Data` and `HttpResponse` against `State` and `IntoResponse`) read naturally only on their own.
- **A shared crate for the templates' common code.** Rejected: a template is copied into the user's project and must build alone. The drift test keeps the copies identical instead.
- **Inferring the framework from `extractors`.** Rejected (see A1).
- **`utoipa-axum`'s router and `tower_governor`.** Rejected (see A4 and A5).

## Consequences

- An actix project's generated output is unchanged. Only `features/README.md` and the scaffolded `AGENTS.md` word the wiring the same way for both frameworks.
- `check-arch` flags the other framework's crate outside `db/`, which a 0.6 project mixing both would now see.
- Every framework-specific piece of the generator is reached through `ApiFramework`. A third framework would add a variant and its renderers, not new `match`es elsewhere.
- Two templates means two copies of the shared code, held together by the drift test, which names the file that drifted.
