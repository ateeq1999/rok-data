# The Clients are emitted by the engine, from the contract

Date: 2026-10-31 · Status: accepted

Workspace ADR 0027 has rok emit a monorepo's Clients from the api App's
`openapi.json`, covering the OpenAPI 3.1 subset utoipa emits and no more.
This ADR records where that lives and the shape of what it emits.

**The engine emits them.**

- **Where:** `clients::openapi` reads the document into one model;
  `clients::ts` emits the TypeScript Client from it, `clients::dart` the
  Dart Client, `clients::rust` the Rust Client. `clients::Project` reads the
  `[contract]` and `[clients]` sections of the monorepo's `rok.toml`, and
  `clients::generate` writes a Client in one of three modes: missing files
  only (`init`), up to date (`rok gen`), or drift only (`rok gen check`).
- **Why the engine:** generated files and their marker rules are the
  engine's (workspace ADR 0005, kept so by workspace ADR 0027), and the
  `init` that must emit `clients/ts` into a fresh scaffold is the engine's.
  `rok-cli` delegates: `rok gen` re-exports the contract and calls
  `clients::generate`; it re-declares nothing.

**The subset is closed.** What the reader does not know fails the read,
naming the construct and its JSON pointer: a header or cookie parameter, a
body other than JSON or `application/octet-stream`, `anyOf`, `not`, a
`$ref` outside `#/components/schemas`, a security scheme other than HTTP
bearer, other components, OpenAPI other than 3.1. Annotations (descriptions,
examples, bounds, formats) are read past: a Client's types are the same with
or without them, and the server checks them.

**The TypeScript Client's shape.**

- **Calls:** `api.<tag>.<operation>(path params..., body, query, options)`.
  The tag groups an operation with its feature's; utoipa names operations
  after handlers, so two of a tag may share an `operationId` — each is then
  named after the first segment where their paths part (`verify2fa`,
  `verifyEmail`), or its method on one path.
- **Factories:** `queries.<tag>.<operation>(...)` (`queryOptions`, keyed
  `[tag, operation, ...arguments]`) for every `GET`;
  `mutations.<tag>.<operation>(options?)` (`mutationOptions`, its variables
  the call's one argument or its arguments by name) for the rest;
  `keys.<tag>` to invalidate a tag's queries.
- **Session:** `configure({ baseUrl, token, onUnauthorized })`. The token
  goes only to operations carrying the bearer marker, and only a `401` to
  one of them calls `onUnauthorized` (unless the call says `keepSession`):
  the web starter's "a 401 for the token we sent ends the session", read
  from the spec instead of a per-call flag.
- **Errors:** `ApiError` and `FieldIssue` keep the web starter's shape and
  fallback messages, so its forms keep mapping `422` details to fields.
- **Files:** every file carries `@generated by rok-data-sqlc`; a changed
  one is rewritten, one whose marker is gone is refused without `--force`,
  one no longer emitted is stale.

**The Rust Client's shape** (`clients::rust`, ticket 07).

- **A crate whose manifest is the project's:** the engine emits
  `src/{lib,runtime,types,calls}.rs` and `README.md`; the template
  scaffolds `Cargo.toml` once (package `api-client`, a root workspace
  member, its own gentler lints), so dependencies, TLS and lints stay the
  caller's to tune, and the template keeps no nested `Cargo.toml` that
  `cargo package` would drop.
- **Calls:** `client.<tag>().<operation>(path params..., body, query)`,
  async on `reqwest` (callable from any tokio runtime); each tag a borrowed
  group type, method names the TS Client's in `snake_case`. Path
  parameters are percent-encoded; a query is one serde struct (`Default`
  when nothing in it is required).
- **Types:** serde types of the client's own — a caller never compiles
  with the server. Formats are read past (`uuid`, `date-time` are
  `String`). An inline object shaped like a component schema is that
  schema; `allOf` of objects merges into one struct; `oneOf` is an
  untagged enum. A request body's property that may be left out *or*
  `null` is `Option<Option<_>>` (keep it vs clear it); an answer's is an
  `Option`, absent and `null` meaning the same.
- **Session and errors:** `Client` holds the bearer token (`set_token`,
  shared by clones); only operations carrying the bearer marker send it,
  and only a `401` to one of them calls `on_unauthorized` — unless made
  through `keep_session()`, the Rust form of the TS `keepSession`.
  `ApiError` has the TS shape (`status`, `code`, `message`, `details` of
  `FieldIssue`s; status 0 for a transport failure).
- **Emitted rustfmt-clean:** the generated text is what rustfmt writes, so
  a workspace's `cargo fmt --check` passes without formatting generated
  files.

**The Dart Client's shape** (`clients/dart`, the pub package
`api_client`, for the Flutter App of ticket 06).

- **Calls:** `ApiClient(baseUrl:, session:, httpClient:)`, a getter per
  tag (`api.users`, a `UsersApi`) and a method per operation, named as the
  TypeScript calls are: path parameters, then the body, positionally; the
  query parameters by name (`list(page: 2, sort: UserSort.email)`,
  `required` when the document says so); then `options`. Raw bodies and
  answers are `Bytes` (the data and its media type).
- **Models:** a `final class` per object schema with `fromJson`/`toJson`
  (an `allOf` flattened into one class), an `enum` per string enum (its
  wire value kept), a `sealed class` per `oneOf` of objects whose variants
  `implements` it, so an App `switch`es over an answer such as
  `LoginResponse`. The variants are told apart by the keys they require;
  two requiring the same keys are refused. An inline object of the same
  shape as a component (a page's items) is that component's class.
- **Three-state request fields:** a request schema's optional, nullable
  field (the API's `Option<Option<T>>`, "keep" versus "clear") is
  `Nullable<T>?`: left out sends nothing, `Nullable(null)` sends `null`.
  Only schemas no response reaches get it; a response's optional, nullable
  field reads as a plain `T?`.
- **Session:** an interface, `token()` and `expired(token)`, that a Flutter
  App implements on its session store (or builds from two functions). As
  in TypeScript, the token goes only to operations carrying the bearer
  marker, and only a `401` to one of them calls `expired` (unless the call
  says `keepSession`).
- **Errors:** every failure throws `ApiException` (`status`, `code`,
  `message`, and a `422`'s `details` of `FieldIssue`s by field path); no
  answer is status 0 (`network_error`, `timeout`), an unreadable success
  is `invalid_response`.
- **Refused:** what Dart cannot type without guessing fails the emission,
  naming it and where: an object with both properties and
  `additionalProperties`, a `oneOf` of non-objects, a query or path
  parameter that is not a scalar, a name the client takes already.
- **Files:** the Dart files carry `// @generated`, `pubspec.yaml`,
  `analysis_options.yaml` and `.gitignore` a `# @generated` line, which
  the writer's marker check now accepts (legacy words included). The
  package is held to `dart analyze --fatal-infos` under strict casts,
  inference and raw types.

## Considered Options

- **The emitter in `rok-cli`:** the CLI would own generated output and
  `init` could not emit the Client without depending on the CLI.
- **A crate of its own:** another published crate, for code the engine's
  `init` and `rok gen` are the only callers of.
- **Positional query arguments, or one argument object per call:** the
  first breaks when a parameter is added; the second makes every call spell
  `{ path: { id } }`. Path parameters stay positional (they are required and
  ordered by the path), the query stays one object.
- **Exporting the contract in `rok gen check`:** the check would build the
  API. The api App's own test keeps the document honest instead.
- **Dart models through `json_serializable` or `freezed`:** a
  `build_runner` step in every App that uses the client, for code rok
  already generates. The models are plain classes with hand-shaped
  `fromJson`/`toJson`, and the package depends on `http` alone.
- **Dart query parameters as one object per call (as in TypeScript):**
  Dart's named parameters already make each optional and named at the
  call site, without a type per operation.
- **`T?` for every optional, nullable request field:** leaving a field out
  and clearing it could not be told apart, and the API's `PATCH`es tell
  them apart.

## Amended 2026-11-03

- **Layouts.** A `[clients]` entry may be a table with `dir` and
  `layout`. `layout = "sources"` emits only a TypeScript or Dart Client's
  source files, flat in `dir` (no README, manifest or `src/` level), so
  the Client can sit inside the App that calls it (workspace ADR 0027,
  amended the same day). The plain-string form is `layout = "package"`.
  The Rust Client is always a crate.
- **The TypeScript Client's types are zod schemas.** Each component
  schema is emitted as `export const <name>Schema = z.object(...)` with
  `export type <Name> = z.infer<...>`, and `oneOf` as `z.union`.
- **Calls check responses.** Each call parses its response with the
  response schema and throws a `ContractError` (the operation and zod's
  issue paths) on a mismatch, apart from the HTTP `ApiError`. zod strips
  unknown keys, so an older Client keeps working against a newer server.
  Request bodies are sent unchecked; the server validates them.
- **Annotations are read for TypeScript.** "Annotations are read past"
  no longer holds for the TypeScript Client: `minLength`/`maxLength`,
  `minimum`/`maximum`, `pattern` and `format` (`email`, `uuid`,
  `date-time`) become zod rules, so the schemas carry the server's rules.
  The Dart and Rust Clients still read past them.

## Amended 2026-11-06

- **Header parameters are read.** Every generated `PATCH` on a versioned
  table takes `If-Match`, so refusing header parameters left such an
  App without Clients. The reader keeps them as an operation's
  `header_params`, and a cookie parameter stands where "The subset is
  closed" above lists a header parameter: it is still refused.
- **A header is part of the call's options**, named after the header in
  each language's case and required when the document says so:
  - TypeScript: `api.documents.update(id, body, { ifMatch: version })`.
    The options are `RequestOptions & DocumentsUpdateHeaders` (a type
    per operation, its fields documented), not optional when a header is
    required. A `GET` factory takes the headers after its arguments
    (`queries.things.get(id, headers)`, in its key); a mutation's
    variables carry them by name (`mutate({ id, body, ifMatch })`).
  - Dart: a named parameter after the query's,
    `update(id, body, ifMatch: version)`, `required` when the header is.
  - Rust: an argument after the query,
    `client.documents().update(&id, &body, &version)` (`&str`; an
    `Option` when the header may be left out), documented with the
    header's description.
- **Entity tags are quoted for the caller.** The Clients don't surface
  response headers, so the version a caller has is the row's column
  (`revision`), not its `ETag`. The runtimes send a bare value of
  `If-Match` or `If-None-Match` quoted (`3` as `"3"`); an entity tag
  (`"3"`, `W/"3"`) or `*` goes as it is. Other headers go as given.

## Amended 2026-11-10

- **Three states only where the API tells them apart.** A body field
  that may be left out and may be `null` is three-state (Rust
  `Option<Option<T>>`, Dart `Nullable<T>?`, TypeScript `T | null`
  optional) only in a component a `PATCH` body reaches, where leaving it
  out keeps the value and `null` clears it. Elsewhere the two mean the
  same, so the field is plain optional: Rust `Option<T>` (skipped when
  `None`), Dart `T?`, TypeScript `field?: T` for a component only
  non-`PATCH` bodies reach (one a response also reaches keeps `null`, the
  answer's value). A Rust body whose fields are all optional derives
  `Default`. This replaces "every request's optional, nullable field is
  three-state" in the Rust and Dart sections above: a `POST` caller wrote
  `Some(Some(…))` and `Nullable(name)` for nothing.
- **An integer is as wide as its `format`.** The reader keeps an
  integer's `format`, and the Rust Client reads it: `int32` is `i32`,
  `int64` or no format `i64` (was `i64` for every integer). utoipa has no
  `int16` and writes `int32` for an `i16`, so a `smallint` column is an
  `i32`. Bounds (`minimum`/`maximum`) are carried where a Client checks
  values, the TypeScript Client's zod rules; the Rust Client has no
  place for them, and Dart's `int` and TypeScript's `number` are one
  width already, so "Formats are read past" above now means every format
  but an integer's in Rust.
