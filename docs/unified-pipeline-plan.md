## Phase 0.5 — rok-db family rename (workspace ADR 0013) — deferred past 0.2.0

- **Deferred past 0.2.0** (workspace ADR 0013, amended 2026-10-21): the rename
  was never taken, and the family stays `rok-data`. The 0.2.0 window
  had room for exactly one breaking change, and it went to the
  pipeline (the ORM chains, the front door, the axum backend, the
  vertical slice). A crate rename has to land whole — the crates, the
  dependency paths, the doc links, the env var, the marker forms and
  the generated dependency fragments in one release, with the crates.io
  names checked before the tag (workspace ADR 0008). Half of it is worse than
  none: the tree would carry two families, and the release would
  publish names nobody generates.
- What it does, when it happens: the crates become `rok-db` (facade),
  `rok-db-core`, `rok-db-macros`, `rok-db-sqlc`, `rok-db-codegen`;
  workspace members, dependency paths and doc links follow
  mechanically.
- Generated marker headers accept a third form (`@generated by
  rok-db-sqlc`) alongside both workspace ADR 0005 legacy forms.
- Env var: `ROK_DATA_SQLC_TEST_DATABASE_URL` becomes
  `ROK_DB_SQLC_TEST_DATABASE_URL` (CI and AGENTS.md updated in the
  same change).
- Generated dependency fragments pin `rok-db = { … }`; templates and
  fixtures updated together.
- NOT renamed (then or now): the journal table `_rok_data_migrations`
  (deployed DB surface, workspace ADR 0004) and the `rok` binary name (workspace ADR
  0002).
- The 0.2.0 release publishes the `rok-data*` crates — the names in
  `AGENTS.md`'s Releasing section — and the crates.io availability
  check covers those names, not the `rok-db` ones.
- Acceptance (when it happens): full gate suite green (fmt, clippy
  `-D warnings`, workspace tests incl. `module_fixtures`); README and
  `docs/cli-reference.md` show the new names; legacy alias suites
  still pass.

## Phase 2 — core `.with()` + ORM-backed engine output

- `rok-data-core` / macros / facade: With-loading —
  `Select::with(relation)` chaining returning rows that carry their
  loaded relations; per-relation `load()` loaders unchanged (root
  glossary: *With-loading* vs *Loader*). Shape adopted from the
  toasty study: an include is a typed relation path with its own
  chainable sub-builder (`.filter()` / `.order_by()`); loading runs
  as batched follow-up queries (no join-struct rows); load state is
  read without panicking — an explicit `try_get`-style accessor
  beside the row, never toasty's `Deferred::get()` panic. The derive
  guards the generated method names with a reserved-word table: a
  relation whose name is a Rust keyword is emitted as a raw identifier
  (`r#type`), so the generated code compiles.
  - **Done (2a)**: `Relation` trait over the relation constants
    (`HasMany`/`HasOne`/`BelongsTo`); `Include` (bare constant or
    `Include::new(..).filter().order_by().limit().offset()` on the
    batch); `PackedInclude` value-erasing per relation behind two
    closures (children SQL, rows→state assembly); `Loaded` view
    (`rows()`, `loaded(relation)`, `try_get(relation, owner)` —
    `Option<Option<&T>>` for one-rows, never a panic); identity is
    the relation type plus its defining foreign-key column, so two
    relations over the same pair through different FKs coexist
    (a repeated identity means last shaping wins). Execution rides a
    shared `Journey` (`&Db`, `&mut Tx`, `&PgPool`, `&mut
    PgConnection`), so a query's rows and each include's batch share
    one pool or one transaction; `WithSelect` mirrors
    `.filter()/.order_by()/.limit()/.offset()` and adds more
    includes; terminals are `all()` (+ `Loaded`) only — `stream()`
    and paging of included rows stay out for now. The derive's
    relation accessors are guarded by a reserved-word table (a keyword
    name becomes `r#type`). DB-gated facade test
    `with_loads_relations_beside_the_rows` passes against real
    PostgreSQL; full workspace gate green. Depth is one level: an
    include's base cannot itself carry includes.
- Engine db-module templates rewritten onto the facade: `Model`
  structs, typed column consts, chainable queries; the `XFilter`
  serde surface stays byte-compatible in JSON but compiles to typed
  `Expr` conditions; `NewXxx`/`UpdateNote`-style patch semantics
  preserved (None = unchanged, Some(None) = NULL, empty patch returns
  the current row, generated-id fallthrough); m2m rides the join
  model for now.
  - **Done (2b Slice A)**: per-table data layers emit the ORM
    chains — read `Model::query().filter(..).first(executor)`,
    list `.all(executor)`, create
    `Model::create().set(..).exec(executor)`,
    update `Model::update_all().filter(..)
    .set(..).returning_one(executor)`, delete
    `Model::query().filter(..).delete(executor)` — every generated
    function returns `rok_data::Error`; `filter.rs`, `search.rs`,
    `search_after`, and `listing.rs` stay QueryBuilder-based with
    byte-identical SQL (query-file `queries.rs` and joined reads
    stay sqlx by design). Chain framing lives in the engine's
    emitter (one line when the chain through `.await` is ≤ 60 px,
    frame otherwise; `MAX_WIDTH` 100). The `Model` derive accepts
    no-primary-key tables, composite SQL types ride
    `Value::CustomType` (`money`, ranges, `timetz`, inet/cidr,
    macaddr, bytea arrays) behind the new `ipnetwork` and
    `mac_address` facade features, and fixtures/examples/templates
    pin rok-data 0.2 with the features the columns call for.
    Workspace version 0.2.0; engine unit suite 240.
- API features: new axum + utoipa generator under the same compile bar
  as the actix fixtures (`deny(missing_docs)`:
  pedantic clippy); actix continues from the current templates.
  - **Done (T4a)**: the engine's API generator has two backends. The
    `[api] framework` key (or `-w/--api-framework`) picks one: `actix_web`
    (the default, byte-identical output) or `axum`. The per-framework
    emission sits in `generator/api/actix.rs` and `generator/api/axum.rs`
    (and the shared tools' templates in `generator/api/shared/`), chosen in
    one place (`generator/api/framework.rs`); the bodies, the service, the
    listing and the OpenAPI document are shared. The axum fixture
    (`tests/axum-app`, listed in the workspace `exclude`) proves it under
    the same bar as the actix one: `deny(missing_docs)`, the selected
    pedantic lints, `-D warnings`, `check-arch` and rustfmt.
  - **Done (Phase 4, this release)**: `check-arch`'s rule 1 names the
    configured framework now. It reads `[api] framework` from the same
    config file the generation does: under the default `actix_web`
    everything prints exactly as before (texts byte-identical, pinned by
    tests), and under `axum` it polices `axum` over the same allowed-file
    set the axum emission fills. The rule texts are one source per
    framework; the templates' `AGENTS.md`s already stated their own
    framework (each pinned to `check-arch`'s rendering now), and
    `docs/guide/architecture.md`, the engine README, the troubleshooting
    page and engine ADR 0016 name what rule 1 watches.
- Acceptance: the engine unit suite (240) passes; generated data
  layers no longer contain raw sqlx function modules (query files
  and joined reads keep their explicit sqlx bodies).

## Phase 3 — front door wiring

- `rok-data-cli`: `rok init [NAME] [--template axum] [--schema PATH]`
  scaffolds a Template (complete app incl. `main`/`app`/`config`
  `/error`/OpenAPI wiring), with the scaffolded-file policy (written
  once, never rewritten).
  - **Done (T4b)**: the second template, `axum`
    (`templates/axum-api/`, in the workspace `exclude`): the actix
    template's twin, with the same `users` and `audit-log` features, the
    same wire standard, the same contract test against the axum starter's
    document, and its own README, `AGENTS.md` and migration. Its
    configuration selects the backend (`extractors = ["axum"]`, `[api]
    framework = "axum"`), and the engine's template table knows it, so
    `rok init --template axum` copies it and the `--template` error lists
    both. CI checks it in like the actix one: regenerated with no drift
    (`ROK_DATA_SQLC_UPDATE_EXPECTED=1` writes it), rustfmt-clean,
    `cargo clippy --all-targets -- -D warnings` under the template's
    strict lints (`deny(missing_docs)`, the selected pedantic lints, no
    `unwrap`/`expect`/`panic`), `check-arch`, and its own tests.
- `rok gen` / `rok gen check`: flags `--config --schema --migrations-dir
  --migration NAME --allow-destructive --rename OLD=NEW --strict --json`.
  - **Done (T2)**: the root `rok gen` is the unified front door: the
    engine's generator writes the data layer (`src/db/**`), the shared
    tools and the API features (`src/features/**`) from the project's
    schema dir, and `--migration NAME` stages a `NNNN_name.up.sql` /
    `.down.sql` pair with the codegen crate's new narrow
    staging API (`rok_data_codegen::staging`, the diff engine without a
    whole crate) — at T2 into the schema dir itself, which held the
    truth (plain `*.sql` files) and the history (the staged pairs); the
    generator reads the truth only, so a staged migration is never
    applied twice. The staged migration's base is the snapshot
    `.rok-schema.json` — hidden, not a `*.sql` file, and not the
    engine's registry (`src/db/schema.json`, which holds the schema as
    it is *now*). `rok gen check` is the CI mode: nothing is written,
    the drift is reported, exit 1 on drift. The settings file is the
    unified `rok.toml` (`[generate]`, workspace ADR 0011); the engine's
    `rok-data-sqlc.toml` stays readable. The legacy `rok generate` and
    `rok sqlc …` are untouched. (Since ticket (c) the snapshot sits in
    the history dir and the truth dir holds no pairs — see the next
    ticket's note.)
  - **Open (Phase 0)**: the unified `rok.toml`'s `[generate]` section
    and the legacy whole-crate generator's `[generate]`/`[gen]` section
    share a name and an `output` key with two meanings; the legacy
    reader must be reconciled with the unified one, and `rok init`
    should write `rok.toml` (it still writes the engine's file, so the
    "legacy name" notice of workspace ADR 0011 is not printed yet).
  - **Done (ticket (c))**: the truth and the history live in one dir
    each. The settings resolve the truth dir (`[generate] schema`;
    `rok init` and `rok sqlc init` now seed a `schema/` truth dir) and
    the history dir (`[generate] migrations`, default `migrations`;
    `rok gen --migrations-dir` overrides the file). `rok gen --migration`
    stages the pairs and the `.rok-schema.json` snapshot into the
    history dir, and the staging's default keeps both dirs = `migrations`,
    so a legacy same-dir project stages as before. The loader skips
    hidden entries (the snapshot among them), so the loader of this
    plan — `rok migrate up` — reads that dir. The staged side got the
    remaining ALTER vocabulary: an `ALTER TABLE` the truth carries folds
    into the truth's tables (`an_alter_folded_into_the_table_stages_nothing`
    in `crates/rok-data-codegen/src/ddl/tests.rs` replaces the old
    drop-then-add pin), and a clause the model cannot represent still
    rides the pair as an `Extra` step with the undo its `-- rok:down`
    marker supplied. The `--migration` advice now names `rok migrate
    up` (+ `--dir` when the history dir is not `migrations`), not a
    `psql` invocation the loader could not answer. `rok gen check`
    guards the history too: a truth that moved on since the last staged
    pair is drift, and it is a finding of its own — the prose names the
    migration the truth moved on from and the version the pair would
    take (`0002_pending`), and `--json` carries it in
    `pending_migration`. Deliberate: the check names no file that does
    not exist (no synthesized pair among the missing files), because the
    pair is the user's to name and to write; the gate itself is
    unchanged — the run still fails (exit 1).
- Legacy aliases stay verbatim-forwarding (`rok sqlc` →
  `run_from`); root help marks both `rok generate` and `rok sqlc` as
  superseded, removal deferred to 1.0; `docs/cli-reference.md`
  updated in the same change.
  - **Done (T3)**: the root help marks `rok generate` and `rok sqlc` as the
    legacy surface — still supported, still forwarded verbatim to
    `rok_data_sqlc::cli::run_from` — superseded by the front door (`rok init`
    scaffolds, `rok gen` generates), with the removal deferred to 1.0. The
    per-command descriptions carry the same marker, and
    `docs/cli-reference.md` (the contract), the READMEs,
    `docs/architecture.md` and `docs/feature-matrix.md` say the same. No
    flag, alias, output or exit code changed.

## Phase 4 — vertical slice: `examples/api/`

- Workspace-excluded example crate (own `[workspace]` table, listed in
  exclude, per AGENTS.md invariant 7) demonstrating the full chain:
  `schema/` with two small `.sql` files → Template + `rok gen` →
  ORM models, migration pairs, axum features; CI compile-checked.
  - **Done (T5)**: `examples/api` — the axum template's hand-written half
    (copied and adapted, never linked), a schema dir `schema/` with two
    truth files (`library.sql`, `loans.sql`) and the staged migration
    pairs beside them (`0001_init`, `0002_add_loans`), the generated
    `src/db/**` (the ORM chains) and `src/features/**` (the axum
    features), and the unified `rok.toml` (`[generate] schema = "schema"`,
    `[api] framework = "axum"`). The crate is workspace-excluded (its own
    `[workspace]` table, and an entry in the root `Cargo.toml`'s
    `exclude`), and the repository's gate
    (`crates/rok-cli/tests/fixture_compile/example_api.rs`) proves it:
    `rok gen check` finds no drift, the staged pairs are the ones
    `rok gen --migration` writes, and the crate passes rustfmt, the lint
    gate and its tests (the API tests against PostgreSQL when a database
    is configured; they skip otherwise).
  - **Done (the engine's half of it)**: a truth file can carry an
    `ALTER TABLE` now (engine ADR 0017). The engine's
    schema parser honors the `-- rok:down` section the truth carries
    (the codegen's own vocabulary: a marker line's next statement is
    the undo of the statement immediately before the marker), where it
    used to apply the undo as a statement of its own — `ALTER TABLE
    books ADD COLUMN isbn` and its `-- rok:down` / `DROP COLUMN` undo
    now leave the generated data layer with the column. A misplaced
    marker is refused engine-side, with the codegen's rule wording: a
    leading marker errors ("`-- rok:down` must directly follow the
    statement it undoes" — the one case the codegen refuses with the
    same words), and a marker whose undo never joined it — a blank line
    parted them, or nothing follows the marker at all — errors
    ("`-- rok:down` must be followed by the SQL that undoes the
    statement above it"); there the codegen either refuses the
    orphaned statement itself ("rok can't undo this statement by
    itself…") or, for a purely trailing marker, loses it silently,
    which the engine may not. The engine's pre-pass scans the truth
    like the codegen's statement splitter does, so a `rok:down` line
    inside a string literal is that literal's text, in either tool.
  - **Done (ticket (c))**: the staging's half of the ALTER vocabulary
    arrived: an `ALTER TABLE` the truth carries folds into the truth's
    tables instead of riding the pair as its own step (pinned by
    `an_alter_folded_into_the_table_stages_nothing` in
    `crates/rok-data-codegen/src/ddl/tests.rs`, which replaced the old
    drop-then-add pin), and the loader reads the separate history dir —
    the Phase 3 note names the layout. The example and the templates
    ship truth and history in one dir each now, so nothing next to the
    pairs applies a change twice.
  - **Done (this release)**: `check-arch`'s rule 1 names the configured
    framework now: it reads `[api] framework` from the same config
    file the generation does. Under the default `actix_web` every text
    stays byte-identical (pinned by engine and CLI tests), and under
    `axum` it polices `axum` over the allowed file sets of the axum
    generation. The scaffolded `AGENTS.md`s already named their own
    frameworks — each pinned to `check-arch`'s rendering for its
    framework now — so the templates' bytes needed no rewrite; the
    architecture guide, the engine README, the troubleshooting page and
    engine ADR 0016 say what rule 1 watches.
- Docs: `README.md`, `docs/getting-started.md`,
  `docs/feature-matrix.md` updated to sell the new front door.
  - **Done (T5)**: the root README's quick start leads with `rok init …

## Phase 6 — 0.3.0: the model-shaped data layer

The spec of record: `docs/specs/0.3.0-model-shaped-data-layer.md`
(proposed 2026-10-22). The decisions: workspace ADR 0014 (the verbs live
on the model), workspace ADR 0015 (conventions are inferred, with explicit
opt-outs), engine ADR 0018 (the generated model's shape).

Breaking release: the runtime's public surface and the generated output
both change; no deprecation staging (workspace ADR 0014). The legacy
command surfaces (`rok generate`, `rok sqlc …`) are not touched, and
`docs/cli-reference.md` does not change (no command, flag, output or exit
code changes).

Task graph, in order:

- **M0 — the records.** The three ADRs above, this phase, and the spec's
  acceptance. (Done.)
- **M1 — the runtime surface** (spec D2/D3): `create()` →
  `insert_builder()`, `save()` removed in favour of `update()`, `exists()`
  added to the model; the chain gains `get()` (alias of `all`), `chunk()`
  and `where_`; `where_` also aliases the model's `filter`. Proven in
  the facade's integration suite.
  - **Done (M1)**: the runtime carries the renamed verbs (`insert_builder`,
    `update`, `update_only`) and the new ones (`exists`, `get`, `chunk`,
    `where_` at both levels); `chunk` windows the existing stream, so one
    query serves every window. `save_only` became `update_only` for the
    same reason `save` went: the ambiguous word does not survive. The
    engine's emission, `Tracked`, the templates and `examples/api` follow
    the renames, and the corpus was refreshed through the sanctioned
    `ROK_DATA_SQLC_UPDATE_EXPECTED=1` runs. `Tracked::save` and the
    `before_save`/`after_save` hooks keep their names on purpose — a
    tracked record only ever writes changed columns, so the
    insert-or-update ambiguity never reaches them (spec D9). The
    migration guide carries the before/after.
- **M2 — the inferred conventions** (spec D4): the derive infers managed
  timestamps and soft deletes from the field names; `#[rok(no_timestamps)]`
  and `#[rok(no_soft_delete)]` are the opt-outs; the existing markers keep
  working.
  - **Done (M2)**: the derive infers the conventions from the model's own
    fields — `created_at` and `updated_at` are managed timestamps, a
    `deleted_at` is the soft-delete column — and the two opt-outs turn the
    inference off. A marker with its opt-out (`#[rok(timestamps)]` with
    `#[rok(no_timestamps)]`) fails the derive instead of guessing, and an
    inferred managed column cannot be `generated` as well. The generator
    applies the same rules and stops writing the markers: it writes the
    opt-out where the database owns the column — a timestamp column whose
    default is not `now()`, a `deleted_at` the database fills or that
    cannot carry a soft delete — and nothing where the inference already
    says the right thing. A `managed_columns` column is the data layer's
    whatever its default, and the `soft_delete_column` convention still
    wins: it names the soft-delete column, whatever its name. The corpus
    was refreshed through the sanctioned `ROK_DATA_SQLC_UPDATE_EXPECTED=1`
    runs.
- **M3 — the generated model's shape** (spec D6/D7/D8): relation
  attributes derived from the schema's foreign keys (`User::POSTS`,
  `user.posts()`), named scopes (model entry + chain method through the
  runtime's `Scope` trait). Pinned in the module-fixture corpus.
  - **Done (M3a — the scopes)**: the runtime exports the `Scope` trait
    (the machinery that applies a scope function to a chain) and the
    `declare_scopes!` macro; the derive reads
    `#[rok(scopes(popular = path::to::popular))]` and writes the model's
    entry (`User::popular()`) and a per-model trait (`UserScopes`) whose
    methods are the chain's (`User::popular().active()`). A scope
    function is `fn(&Select<M>) -> Select<M>`; the derive refuses a
    malformed attribute and a name the runtime already uses. The
    relation half (M3b) is the next ticket, and the engine's generated
    code is untouched so far.
- **M4 — the typed write spine** (spec D5): `User::create(&db, NewUser)`,
  `User::patch(&db, id, UpdateUser)`, `User::destroy(&db, id)`; the
  module's functions stay as thin wrappers.
- **M5 — the docs and the release**: the glossaries (Model, Scope; Resource
  and Query chain rewritten), `docs/getting-started.md` rewritten,
  `docs/migration-guide.md` gains the 0.3.0 before/after, the root
  `CHANGELOG.md` gains `## [0.3.0]`, the feature matrix and the
  architecture doc follow, the workspace version becomes 0.3.0 and the
  release is tagged per workspace ADR 0008.

The three testing seams the spec names: the facade's integration suite, the
engine's module-fixture corpus (refreshed only through
`ROK_DATA_SQLC_UPDATE_EXPECTED=1`), and the compile fixtures plus
`examples/api` (no drift under `rok gen check`).

### Additions (review round, 2026-10-21)

Deferred refactors (judgement calls the two-axis review flagged, recorded
here rather than started — none of them is a bug):

16. The API generator's framework dispatch
    (`crates/rok-data-sqlc/src/generator/api/framework.rs`): every
    method of the `Framework` enum is a `match` on the backend (nineteen
    dispatches), so a third backend means nineteen edits — a per-backend
    trait would remove the cascade, but it touches every emission site,
    so it waits for the backend that makes it pay.
17. `One<O, T>` and `Many<O, T>`
    (`crates/rok-data-core/src/relation/loaded.rs`): the two structs
    duplicate about sixty lines of map handling — a shared base would
    remove it, but the two shapes (one record or many per owner) differ
    in every method that matters, so the duplication stays cheap to
    read.
