# Spec — 0.3.0: the model-shaped data layer

Status: proposed · Release: 0.3.0 (breaking) · Supersedes nothing · Implements
workspace ADR 0014 and ADR 0015 (to be written with this work).

## Problem Statement

A developer who knows Eloquent cannot write this framework without relearning
it, and the friction is not in one place — it is in the shape of every call.

Today a query looks like this:

```rust
User::query()
    .filter(User::AGE.gte(18))
    .order_by(User::AGE.desc())
    .limit(10)
    .all(&db)
    .await?;
```

and a write looks like this:

```rust
User::create()
    .set(User::EMAIL, "a@b.c")
    .set(User::NAME, "Ada")
    .exec(&db)
    .await?;
```

Five separate things are wrong from a Laravel-shaped point of view, and each
one costs a developer a moment of hesitation:

1. **The verbs are on the wrong object.** Eloquent puts `find`, `all`,
   `where`, `create` on the model class. Here the model is a passive row
   struct and the verbs live in sibling modules (`users::read::get_by_id`),
   so every call site is a path the reader has to look up.
2. **The conventions must be declared, not inferred.** Eloquent needs no
   ceremony: a `created_at`/`updated_at` pair *is* the signal, a `deleted_at`
   column *is* the signal. Here a model must say `#[rok(timestamps)]` and
   `#[rok(soft_delete)]` or it silently gets neither — and the generator
   does not emit them at all, so a generated model has no ORM-managed
   timestamps even though the table has the columns.
3. **The write path has no "save a new row" verb.** `save()` updates by key
   and fails on a row that is not there; `insert()` inserts one row struct;
   there is no `Model::create([...])`-shaped entry that takes a typed input,
   which is the one call every Laravel developer reaches for first.
4. **The vocabulary is invented rather than shared.** `filter` is not the word
   anyone means by "a WHERE clause", and the engine's own `XFilter` struct
   (a typed search input) already owns the word "filter" — two different
   things, one word. Scopes exist only as closures applied to a builder;
   there is no named scope. Relations are declared by hand on hand-written
   models and are **not** declared at all on generated ones, so a generated
   model has no `User::POSTS` and no `user.posts()`.
5. **Every write is one column at a time.** Mass assignment is the shape
   developers expect, and the type system is the right place to express it
   (a typed create input), not a runtime allow-list.

The result is a data layer that is technically fluent but not *legible*: a
reader who knows the SQL and knows Eloquent still has to learn a private
vocabulary before they can read a query.

## Solution

The data layer becomes **model-shaped**: the model is the object you call, the
conventions are inferred from the schema and the field names, and the write
path is typed.

Concretely, for 0.3.0:

- **Reads and query entry points live on the model.** `User::find(&db, id)`,
  `User::all(&db)`, `User::count(&db)`, `User::filter(expr)`, `User::query()`.
  The generated code emits these as inherent methods on the generated model,
  so a call site reads `User::find(&db, id)` instead of
  `users::read::get_by_id(&db, id)`.
- **Conventions are inferred.** A model with `created_at` and `updated_at`
  fields gets ORM-managed timestamps; a model with a `deleted_at` field gets
  soft deletes; `#[rok(no_timestamps)]` and `#[rok(no_soft_delete)]` turn them
  back off. The generator applies the same rules and only writes the opt-outs.
- **Writes are typed.** The generator's create input (`NewUser`) and update
  patch (`UpdateUser`) become the model's own write API:
  `User::create(&db, input)`, `User::patch(&db, id, patch)`,
  `User::destroy(&db, id)`. Row-level writes are explicit:
  `user.insert(&db)`, `user.update(&db)`, `user.delete(&db)`.
- **Scopes are named.** A scope is a function from a query chain to a query
  chain; the model declares it, and the derive gives it a chainable entry
  (`User::popular()`) that composes with other scopes.
- **Relations are declared by the generator.** Foreign keys found in the
  schema become `belongs_to`/`has_many` attributes, so a generated model has
  `User::POSTS` and `user.posts()` without the developer writing them.
- **The vocabulary is shared where the language allows it.** `where` is a
  Rust keyword, so `filter` stays the canonical verb (the Diesel/SeaORM
  convention) and `where_` is offered as an alias for developers who want
  the Eloquent spelling. `get()` joins `all()` as the chain terminal.

The release is **0.3.0 and breaking**: the runtime's public surface changes
and the generated output changes. A migration guide carries the before/after.

## User Stories

### The developer who writes SQL first

1. As a developer who keeps the schema in a folder of `.sql` files, I want the
   generator to give me models with the conventions already applied, so that
   I do not have to restate in every model that the table has timestamps.
2. As a developer who keeps the schema in a folder of `.sql` files, I want a
   generated model to expose its relations (`User::POSTS`, `user.posts()`),
   so that I can navigate the schema from the code without hand-writing
   relationship attributes.
3. As a developer who keeps the schema in a folder of `.sql` files, I want the
   generated model to be the place where reads and writes are called, so that
   the data layer reads like the models I wrote.
4. As a developer who keeps the schema in a folder of `.sql` files, I want
   `rok gen check` to fail when the generated code no longer matches the
   schema, so that a stale data layer never reaches a review.
5. As a developer who keeps the schema in a folder of `.sql` files, I want the
   generator to leave my own code alone, so that I can hand-edit the service
   layer without the generator overwriting it.
6. As a developer who keeps the schema in a folder of `.sql` files, I want
   `updated_at` to move when the row changes, so that I do not need a
   database trigger to know when a row was last touched.

### The developer who writes models by hand

1. As a developer writing a model by hand, I want the table name inferred
   from the struct name when I do not say otherwise, so that I write less
   boilerplate.
2. As a developer writing a model by hand, I want a model with `created_at`
   and `updated_at` fields to manage those timestamps itself, so that I do
   not write `#[rok(timestamps)]`.
3. As a developer writing a model by hand, I want a model with a `deleted_at`
   field to soft-delete by default, so that I do not write
   `#[rok(soft_delete)]`.
4. As a developer writing a model by hand, I want to turn those inferences
    off when a table genuinely does not want them, so that I can opt out
    without giving up the convention everywhere else.
5. As a developer writing a model by hand, I want a primary key to be
    inferred from an `id` field, so that I do not write `#[rok(primary_key)]`
    for the common case.
6. As a developer writing a model by hand, I want the row's own verbs to be
    explicit — insert, update, delete — so that a save never surprises me
    with an insert I did not intend.
7. As a developer writing a model by hand, I want to find a row by its key
    without building a query chain, so that the common read is one call.
8. As a developer writing a model by hand, I want a missing row to be an
    error I can catch by type, so that a handler can turn it into a 404.

### The developer reading rows

 1. As a developer reading rows, I want to start a query from the model
    itself, so that the entry point is the same object the row type is.
 2. As a developer reading rows, I want to filter with a typed column
    constant, so that a renamed column is a compile error rather than a
    runtime surprise.
 3. As a developer reading rows, I want the chain terminal to be called
    `get()`, so that the code I write from Eloquent muscle memory compiles.
 4. As a developer reading rows, I want `filter` and `where` to mean the same
    thing, so that I can use whichever word I reach for.
 5. As a developer reading rows, I want to load a relation in the same chain
    that fetches the rows, so that I do not write one query per row.
 6. As a developer reading rows, I want a relation I did not ask for to read
    as absent rather than panic, so that a forgotten `with` is not a crash.
 7. As a developer reading rows, I want to page through a large table without
    holding it all in memory, so that a report does not exhaust the process.
 8. As a developer reading rows, I want to process a large table in chunks,
    so that I can bound memory and still see every row.
 9. As a developer reading rows, I want a count and an existence check on the
    chain, so that I do not fetch rows only to count them.
10. As a developer reading rows, I want the same query to run against the
    primary or a replica, so that a read-heavy page does not load the writer.

### The developer writing rows

 1. As a developer writing rows, I want to create a row from a typed input
    that names only the columns a caller may set, so that a request body
    cannot reach a column it was not meant to.
 2. As a developer writing rows, I want to create a row in one call, so that
    the common write is not three chained calls.
 3. As a developer writing rows, I want to patch a row without loading it
    first, so that a partial update is one round trip.
 4. As a developer writing rows, I want a patch that leaves a column alone
    when the caller says nothing about it, so that "not mentioned" and "set to
    null" stay distinguishable.
 5. As a developer writing rows, I want to delete a row by its key without
    loading it, so that a delete is one round trip.
 6. As a developer writing rows, I want a delete to be a soft delete when the
    table has a `deleted_at` column, so that a mistaken delete is recoverable.
 7. As a developer writing rows, I want to restore a soft-deleted row, so
    that recovery is a first-class operation.
 8. As a developer writing rows, I want to write one row struct I built
    myself, so that a value computed elsewhere can be persisted directly.
 9. As a developer writing rows, I want the insert builder to stay available
    for the cases a typed input does not cover (raw expressions, conflict
    handling), so that I am not boxed in by the friendly path.
10. As a developer writing rows, I want an update to fail loudly when the row
    is gone, so that a lost update is not silent.

### The developer relating rows

 1. As a developer relating rows, I want a generated model to declare its
    relations from the foreign keys in the schema, so that the relations I
    see in the database are the relations I can traverse in the code.
 2. As a developer relating rows, I want a relation to be usable as a query
    chain from a row (`user.posts()`), so that I can add my own conditions.
 3. As a developer relating rows, I want a loaded relation to be read by the
    same constant that asked for it, so that the read and the request cannot
    drift apart.
 4. As a developer relating rows, I want a soft-deleted related row to be
    hidden like any other, so that a relation does not leak deleted rows.

### The developer scoping queries

 1. As a developer scoping queries, I want to name a reusable constraint and
    call it by name (`User::popular()`), so that the constraint has one
    definition and many call sites.
 2. As a developer scoping queries, I want named scopes to compose
    (`User::popular().active()`), so that I do not have to write the
    combination out each time.
 3. As a developer scoping queries, I want a global scope on a model, so that
    every query for that model carries it by default.
 4. As a developer scoping queries, I want to opt out of a global scope for
    one query, so that an administrative query can see everything.

### The developer keeping the API layer honest

 1. As a developer writing an HTTP handler, I want the data layer to offer
    the same verbs for every table, so that a handler for one table is a
    template for the next.
 2. As a developer writing an HTTP handler, I want a "not found" answer to be
    a distinct error, so that I can map it to 404 without string matching.
 3. As a developer writing an HTTP handler, I want a validation failure to
    name the field that failed, so that the caller can be told what to fix.
 4. As a developer writing an HTTP handler, I want the generated API feature
    to keep working unchanged, so that the data layer's new shape does not
    force a rewrite of my handlers.

### The developer upgrading

 1. As a developer with an existing project, I want a guide that lists every
    renamed call with its replacement, so that I can upgrade without reading
    the diff.
 2. As a developer with an existing project, I want the upgrade to be one
    release, so that I regenerate once and fix the compiler errors the
    compiler finds for me.
 3. As a developer with an existing project, I want the generator to tell me
    what changed in the generated files, so that I can review the diff.
 4. As a developer with an existing project, I want the release notes to say
    plainly that the data layer's surface changed, so that I am not surprised
    by a breaking change.

### The maintainer of the framework

 1. As a maintainer, I want the runtime's public surface to be small and
    named consistently, so that the docs can be written once.
 2. As a maintainer, I want the words in the code to be the words in the
    glossary, so that "filter", "scope", "resource" and "model" each mean
    one thing across the workspace and the engine.
 3. As a maintainer, I want the generated code and the hand-written code to
    speak the same dialect, so that a developer who learned one has learned
    both.
 4. As a maintainer, I want the decisions behind this shape recorded, so that
    a future reader does not "fix" the naming back to something else.
 5. As a maintainer, I want the framework's own example to use the new
    surface, so that the example is the specification.

## Implementation Decisions

### D1 — The release

- The work ships as **0.3.0, breaking**. The runtime's public surface
  changes (renames, removals, additions) and the generated output changes.
- The framework is pre-1.0 and `docs/migration-guide.md` already exists for
  exactly this; a staged deprecation was rejected because it doubles the
  surface area and makes every project regenerate twice for no user benefit.
- The legacy surfaces (`rok generate`, `rok sqlc …`) keep their flags,
  outputs and exit codes; they are not touched by this work.

### D2 — The model's surface (the shape of a call)

The verbs a caller reaches for live on the model. On the runtime's `Model`
trait, the static (type-level) verbs are:

| Verb | Signature | Notes |
| --- | --- | --- |
| `query` | `fn query() -> Select<Self>` | unchanged |
| `filter` | `fn filter(expr: Expr<Self>) -> Select<Self>` | the where-clause entry; `where_` is an alias |
| `all` | `fn all(executor) -> Result<Vec<Self>>` | unchanged |
| `find` | `fn find(executor, key) -> Result<Option<Self>>` | unchanged |
| `find_or_fail` | `fn find_or_fail(executor, key) -> Result<Self>` | unchanged |
| `find_many` | `fn find_many(executor, keys) -> Result<Vec<Self>>` | unchanged |
| `count` | `fn count(executor) -> Result<i64>` | unchanged |
| `exists` | `fn exists(executor) -> Result<bool>` | **new** (the chain has one today) |
| `insert_builder` | `fn insert_builder() -> Insert<Self>` | **renamed** from `create()` |

The instance (row-level) verbs are:

| Verb | Signature | Notes |
| --- | --- | --- |
| `insert` | `fn insert(&self, executor) -> Result<Self>` | unchanged |
| `update` | `fn update(&self, executor) -> Result<Self>` | **renamed** from `save()` |
| `upsert` | `fn upsert(&self, executor) -> Result<Self>` | unchanged |
| `upsert_on` | `fn upsert_on(&self, executor, columns) -> Result<Self>` | unchanged |
| `delete` | `fn delete(&self, executor) -> Result<()>` | unchanged |
| `force_delete` | `fn force_delete(&self, executor) -> Result<()>` | unchanged |
| `restore` | `fn restore(&self, executor) -> Result<()>` | unchanged |
| `reload` | `fn reload(&self, executor) -> Result<Self>` | unchanged |

`save` is **removed**, not aliased: it is the one Eloquent verb whose meaning
is ambiguous (insert-or-update), and the non-optional typed key makes that
ambiguity unresolvable in Rust. The explicit verbs replace it.

The chain (`Select<Self>`) keeps its shape and gains:

- `get(executor) -> Result<Vec<Self>>` — the alias of `all` that Eloquent
  developers reach for. `all` stays.
- `chunk(executor, size, f) -> Result<()>` — **new**; processes the rows in
  windows of `size`, so a large table does not have to fit in memory.
- `where_(expr)` — the alias of `filter` on the chain.

### D3 — Naming, and the one place the language disagrees

- **`where` is a Rust keyword.** `fn where(..)` does not compile, and the
  raw identifier (`where_`) is awkward to type and to read in a chain, so
  the alias is spelled **`where_`**. The canonical verb therefore
  stays `filter` — the convention Rust ORMs already use (Diesel, SeaORM) —
  and `where_` is provided as an alias on both the model and the chain so
  that Eloquent muscle memory compiles. Generated code uses `filter`.
- `get` joins `all` as a chain terminal; both stay.
- `insert_builder` replaces the old `create()` builder name, because `create`
  is now the model's typed create (see D5) and one type cannot carry both
  meanings.
- `update` replaces `save` on the row; `update_all` (the set-builder entry)
  keeps its name.
- The engine's `XFilter` struct keeps its name: it is a typed search input,
  not a where clause, and the engine glossary already says so.

### D4 — Conventions are inferred, with opt-outs

The derive infers, from the model's own fields:

| Signal | Inference | Opt-out |
| --- | --- | --- |
| fields named `created_at` and `updated_at` | ORM-managed timestamps | `#[rok(no_timestamps)]` |
| a field named `deleted_at` | soft deletes | `#[rok(no_soft_delete)]` |
| a field named `id` | primary key | `#[rok(primary_key)]` for anything else (already the rule) |
| the struct name | table name (pluralized snake case) | `#[rok(table = "...")]` (already the rule) |

The opt-out attributes are **new**; the existing `#[rok(timestamps)]` and
`#[rok(soft_delete)]` markers keep working and mean the same thing (they
become redundant, not wrong).

The generator applies the same rules and therefore stops writing
`#[rok(timestamps)]` and `#[rok(soft_delete)]` — it writes the opt-out only
when the table has the column but the convention says the database owns it.

**Managed timestamps, precisely.** A model with both timestamp columns gets
`now()` written on insert and `now()` written on every update — the runtime's
existing `#[rok(timestamps)]` behaviour, unchanged. For *generated* models the
generator turns this on only when the table's `created_at` and `updated_at`
columns default to `now()`/`CURRENT_TIMESTAMP`; a table whose timestamp
column has a different default keeps the database's value (the generator
writes the opt-out there). A column listed in the `managed_columns`
convention is managed by the data layer regardless of its default.

### D5 — The write spine

- The **create input** (`NewUser`) and the **update patch** (`UpdateUser`) —
  the engine's existing terms — become the model's write API. The generator
  emits them as inherent methods on the generated model:

  | Verb | Signature | Notes |
  | --- | --- | --- |
  | `create` | `async fn create(executor, input: NewUser) -> Result<User>` | typed create; one call |
  | `patch` | `async fn patch(executor, id: UserId, input: UpdateUser) -> Result<Option<User>>` | `None` when there is no such row; an empty patch returns the current row |
  | `destroy` | `async fn destroy(executor, id: UserId) -> Result<bool>` | Eloquent's `destroy`: delete by key without loading |

  `patch` is named `patch` (not `update`) because the instance verb `update`
  already means "write this row's fields", and one type cannot carry both.
  `destroy` is named `destroy` because the instance verb `delete` already
  means "delete this row".
- The generated module keeps the same functions as **thin wrappers** over
  these methods, so the API features and the hand-written service layer keep
  compiling; the wrappers may be removed in a later release.
- The **insert builder** (`Insert<Self>`) stays as the low-level path:
  raw expressions, conflict handling, one column at a time. It is reached
  through `insert_builder()`.
- Hand-written models get the same verbs by writing the input struct and the
  method themselves; the derive does not generate input structs in this
  release (see Out of Scope).

### D6 — The generated code's shape

- The generated model gains the D2/D5 verbs as inherent methods, plus the
  relation constants and accessors.
- The generated model gains **relation attributes derived from the schema's
  foreign keys**: a foreign key column becomes `belongs_to`, and the
  referenced table becomes `has_many` on the other side. A generated model
  therefore has `User::POSTS` and `user.posts()` without the developer
  writing them. Where the schema's foreign key does not name the relation
  unambiguously, the generator emits the explicit form
  (`belongs_to(author = User)`).
- The per-table module keeps what it is good at: the filter/serde contracts,
  the search and listing code, the API-feature wiring and the OpenAPI
  document. The "Resource" term in the engine glossary is redefined from "the
  module the generator writes for one table" to "the API feature of one
  table", so that "model" and "resource" stop overlapping.
- The API features, the OpenAPI document, the filters' JSON shape and the
  patch semantics are **byte-compatible where they are not affected**; the
  data layer underneath them changes.

### D7 — Named scopes

- A scope is a function from a query chain to a query chain:
  `fn(&Select<M>) -> Select<M>`.
- The model declares its scopes the way it already declares its default
  scope — by path: `#[rok(scopes(popular = path::to::popular))]`. The derive
  then emits
  - a chainable entry on the model: `User::popular() -> Select<User>`, and
  - the same-named method on the chain, through a `Scope` trait the runtime
    exports, so scopes compose: `User::popular().active()`.
- The existing `default_scope` (the global scope) and `.unscoped()` are
  unchanged.
- A scope is a free function rather than a method on the model because a
  type cannot carry both a method `popular` and an entry point `popular`.

### D8 — Relations and with-loading

- The semantics do not change: an include is one batched follow-up query, a
  relation never requested reads as absent rather than panicking, and a
  loaded relation is read through the constant that asked for it.
- What changes is that generated models have relations at all (D6), and that
  the relation constants are usable in the same chain as before.
- Soft-deleted related rows stay hidden.

### D9 — What does not change

- The connection is passed at the terminal (`all(&db)`, `get(&db)`,
  `exec(&db)`), not at the head of the chain. A chain stays a pure query
  description: it can be inspected (`to_sql`), reused, and run against the
  primary or a replica.
- `Expr`, `Column`, `Projection`, `Order`, `Page`, `Cursor`, `Loaded`,
  `Include`, `Many`, `One`, `Tracked`, the hooks, the validation rules, the
  tenant and audit machinery, the notifications, the cache, the metrics and
  the migration machinery are unchanged.
- The transaction boundary stays the caller's: `db.transaction(|tx| ..)`.
- The engine's `Filter`/`SortKey`/listing/OpenAPI contracts are unchanged.

## Testing Decisions

**What makes a good test here**: the behaviour a caller can observe — the
SQL a chain produces, the row a call returns, the error a call raises. Not
the shape of an internal builder, not the name of a private helper. A test
that asserts an exact SQL string is good (it pins the contract the developer
reads); a test that asserts "a builder of some kind was constructed" is not.

Three existing seams carry this work; no new seam is introduced.

1. **The facade's integration suite** (the runtime and the derive) — the
   highest seam available for the runtime: hand-written models against a real
   PostgreSQL, plus SQL-shape assertions that run without a database. This
   is where the renamed verbs, the inferred conventions, the new `get`,
   `exists`, `chunk` and `where_` alias, the explicit write verbs and the
   scopes are proven. Prior art: the existing timestamp, relations and
   streaming suites in the facade's test tree, which already mix
   database-backed tests with SQL-shape assertions.
2. **The engine's module-fixture corpus** — the generated data layer's
   expected output. This is where the generated model's verbs, the relation
   attributes, the scope entries and the create/patch/destroy methods are
   pinned, and where a change in the generator's output shows up as a
   diffable expectation. Prior art: the existing module fixtures, which
   already pin the generated read/write/filter modules.
3. **The compile fixtures and the vertical slice** — the templates and
   `examples/api` regenerate, compile under the strict lint bar, and pass
   `rok gen check` with no drift. This is where "the generated code is
   valid Rust that a real application uses" is proven end to end. Prior art:
   the existing fixture-compile gates, which already do exactly this.

The CLI's command contract is unaffected by this work; the existing CLI
suites continue to cover it unchanged.

Database-backed suites keep their current behaviour: they skip with a
printed note when no database URL is configured, and never silently.

## Out of Scope

- **Events and observers.** Eloquent's event system (creating, created,
  updating, observers, `withoutEvents`, `saveQuietly`) is not built. The
  runtime's `Hooks` trait stays as it is.
- **`first_or_create` / `update_or_create`.** Already tracked as a
  post-0.2.0 backlog item; not part of this release.
- **Correlated aggregates** (`with_count`, `with_sum`, `with_avg`,
  `with_min`, `with_max`). Also already tracked in the backlog.
- **Mass-assignment allow-lists** (`fillable`, `guarded`). The typed create
  input and update patch express the same restriction in the type system;
  a runtime allow-list would add a second, weaker mechanism.
- **Default attribute values** (Eloquent's `$attributes`). A column's
  database default, and the optional field in a create input, already cover
  the case.
- **A collection wrapper.** Chains return `Vec<Model>`; Eloquent's
  `Collection` is not introduced.
- **Derive-generated create inputs and update patches.** A hand-written
  model writes its own input struct; the derive does not invent one.
- **`fresh` / `refresh` / `replicate` / pruning.** `reload` covers the
  re-read case.
- **UUID/ULID key traits.** The engine's `primary_key_ids` convention
  already covers generated keys.
- **An artisan-style `make:model`.** `rok init` and `rok gen` are the
  scaffolding path.
- **Any multi-database support.** PostgreSQL only, as decided.
- **Changes to the legacy command surfaces** (`rok generate`, `rok sqlc …`).

## Further Notes

### Deviations from the agreed answers, and why

- **`filter` was not renamed to `where`.** `where` is a Rust keyword and
  cannot be a function name; the alias is spelled `where_` (the raw
  identifier `where_` compiles but reads badly in a chain). The canonical verb
  stays `filter` (Rust ORM convention) and `where_` is added as an alias so
  the Eloquent spelling works. This reverses the "hard-rename to `where`"
  answer from the design round, for a language reason rather than a
  preference — worth a look before the work starts.
- **`save` was removed rather than kept as "insert or update".** Eloquent's
  `save()` decides by whether the key is set; our keys are non-optional typed
  values, so the decision would have to be a sentinel. The explicit verbs
  (`insert`, `update`, `upsert`) replace it.

### Decisions that need a record

- **Workspace ADR 0014** — the model-shaped data layer: the verbs live on
  the model, the module keeps the contracts, "resource" is redefined. Hard
  to reverse (it is the generated code's shape), surprising without context
  (the engine's glossary defines "resource" as the generated module), and a
  real trade-off (module-centric keeps the verbs in one place and out of the
  model's type).
- **Workspace ADR 0015** — conventions are inferred, not declared, with
  explicit opt-outs. Hard to reverse (it is the attribute grammar), and a
  real trade-off (inference is convenient and can be wrong; declaration is
  explicit and is noise).
- **Engine ADR 0018** — the engine's generated model shape: model-centric
  verbs, relation attributes derived from foreign keys, the module's reduced
  role, and the redefinition of "resource".
