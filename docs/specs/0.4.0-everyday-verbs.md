# Spec — 0.4.0: Everyday verbs — the rest of the daily data-layer surface

Status: proposed · Release: 0.4.0 (minor, additive) · Depends on: 0.3.0 (model-shaped data layer) · Implements four workspace ADRs, the next free numbers (0017–0020; to be written with this work).

---

## Problem Statement

The 0.3.0 release made the data layer **model-shaped**: verbs live on the model, conventions are inferred, writes are typed, scopes are named, relations are declared on generated models. But a developer still misses the **daily ergonomics** — the methods they reach for without thinking:

- **Collection operations**: `users.find(1)`, `users.load('posts')`, `users.model_keys()`, `users.to_query()`
- **Query builder sugar**: `where_any`, `where_json_contains`, `where_date`, `union`, `increment_each`, `tap`/`pipe`, `debug()`
- **Pagination shapes**: `simple_paginate` (no count), a paginator JSON shape (`total`, `last_page`, `next_page_url`), cursor `prev`/`next`
- **Relationship verbs**: `has_many_through`, `belongs_to_many` with `attach`/`detach`/`sync`/`toggle`, `where_has`/`where_doesnt_have`, `with_count`/`with_sum`
- **Eager loading**: nested `with`, `load`/`load_missing` on collections, `constrain` on morph loads
- **Serialization control**: `hidden`/`visible` via DTOs, `appends` via `*WithExtrasDto`, per-field date formats
- **Casting**: declarative `#[rok(casts(...))]` for boolean/json/datetime/encrypted/enum, value-object casts, inbound-only casts
- **Model lifecycle**: `first_or_create`, `update_or_create`, `refresh`/`fresh`/`replicate`, `increment`/`decrement`/`touch`, `prunable` (deferred)

Without these, the framework feels **capable but unfamiliar** — every everyday call requires a lookup.

---

## Solution

**0.4.0 adds the missing everyday surface** as additive, non-breaking extensions on top of 0.3.0's foundation. No verbs are renamed or removed; new methods appear on `Model`, `Select`, `ModelCollection`, `Page`, `CursorPage`, and the relation structs. The generator emits them for generated models. Hand-written models opt in via derive attributes.

The work is organized in **vertical slices** — each slice delivers one feature end-to-end (runtime + derive + generator + tests + docs).

## User Stories

### The developer who reads rows

1. As a developer reading rows, I want `ModelCollection::find(key)` and `find_or_fail(key)` so I can look up a model in memory by its primary key.
2. As a developer reading rows, I want `ModelCollection::model_keys()` so I can extract primary keys for `where_in` clauses or bulk operations.
3. As a developer reading rows, I want `ModelCollection::load(&mut executor, &[Relation])` so I can eager-load relations on already-fetched models.
4. As a developer reading rows, I want `ModelCollection::load_missing(&mut executor, &[Relation])` so I only pay for relations not already loaded.
5. As a developer reading rows, I want `ModelCollection::unique()` so I can deduplicate by primary key after a join.
6. As a developer reading rows, I want `ModelCollection::to_query()` so I can turn an in-memory set into a `WHERE id IN (...)` query.
7. As a developer reading rows, I want `ModelCollection::contains(key)` so I can test membership without iterating.
8. As a developer reading rows, I want `ModelCollection::partition(predicate)` so I can split a collection into two by a predicate.
9. As a developer reading rows, I want `ModelCollection::intersect(other)`, `diff(other)`, `except(keys)`, `only(keys)` so I can do set operations by primary key.
10. As a developer reading rows, I want `ModelCollection::fresh(&executor)` so I can reload all models from the database in one query.
11. As a developer reading rows, I want `Select::where_any(columns, op, value)` so I can search multiple columns with one call.
12. As a developer reading rows, I want `Select::where_all(columns, op, value)` so I can require all columns to match.
13. As a developer reading rows, I want `Select::where_none(columns, op, value)` so I can exclude rows where any column matches.
14. As a developer reading rows, I want `Select::where_json_contains(col, path, value)` so I can query JSONB arrays.
15. As a developer reading rows, I want `Select::where_json_contains_key(col, path)` so I can test for JSON key existence.
16. As a developer reading rows, I want `Select::where_json_length(col, path, op, n)` so I can filter by JSON array length.
17. As a developer reading rows, I want `Select::where_date(col, date)`, `where_month(col, month)`, `where_day(col, day)`, `where_year(col, year)`, `where_time(col, time)` so I can filter by date parts without raw SQL.
18. As a developer reading rows, I want `Select::where_column(col1, op, col2)` so I can compare two columns in the same row.
19. As a developer reading rows, I want `Select::where_null_safe_eq(col, value)` so I can treat `NULL = NULL` as true.
20. As a developer reading rows, I want `Select::union(other)` and `union_all(other)` so I can combine result sets.
21. As a developer reading rows, I want `Select::increment_each(&[(col, val)])` so I can atomically increment multiple columns.
22. As a developer reading rows, I want `Select::tap(f)` and `Select::pipe(f)` so I can compose reusable query components.
23. As a developer reading rows, I want `Select::debug()` and `debug_raw()` so I can print the SQL + bindings during development.
24. As a developer reading rows, I want `Select::select_raw`, `where_raw`, `having_raw`, `order_by_raw`, `group_by_raw` so I can escape to raw SQL when the builder isn't enough.

### The developer who writes rows

25. As a developer writing rows, I want `Model::first_or_create(executor, attrs, values?)` so I can atomically find or insert a row.
26. As a developer writing rows, I want `Model::update_or_create(executor, attrs, values)` so I can atomically update or insert.
27. As a developer writing rows, I want `model.refresh(executor)` so I can reload the row (already exists as `reload`).
28. As a developer writing rows, I want `model.fresh(executor)` so I can get a new instance with current DB values.
29. As a developer writing rows, I want `model.replicate(exclude: &[Column])` so I can create an unsaved copy with some fields reset.
30. As a developer writing rows, I want `model.increment(col, by)`, `decrement(col, by)`, `touch()` so I can atomically update counters and timestamps.
31. As a developer writing rows, I want `Insert::insert_get_id(executor)` so I can get the generated PK from an insert.
32. As a developer writing rows, I want `Insert::insert_using(subquery)` so I can bulk-insert from a SELECT.

### The developer who relates rows

33. As a developer relating rows, I want `#[rok(has_many_through(deployments = Deployment::ENVIRONMENT_ID, through = Environment::APPLICATION_ID))]` so I can reach distant relations in one hop.
34. As a developer relating rows, I want `#[rok(belongs_to_many(target = Role, pivot = role_user))]` so I can work with many-to-many.
35. As a developer relating rows, I want `relation.attach(&mut executor, id, pivot_data?)` so I can insert a pivot row.
36. As a developer relating rows, I want `relation.detach(&mut executor, ids?)` so I can remove pivot rows.
37. As a developer relating rows, I want `relation.sync(&mut executor, ids)` so I can replace the pivot set.
38. As a developer relating rows, I want `relation.sync_without_detaching(&mut executor, ids)` so I can add pivot rows without removing others.
39. As a developer relating rows, I want `relation.toggle(&mut executor, ids)` so I can flip attachment state.
40. As a developer relating rows, I want `relation.update_existing_pivot(&mut executor, id, data)` so I can update pivot columns.
41. As a developer relating rows, I want `Select::where_has(relation, fn)` so I can filter parents by related existence.
42. As a developer relating rows, I want `Select::where_doesnt_have(relation, fn)` so I can filter parents by related absence.
43. As a developer relating rows, I want `Select::where_relation(relation, col, op, value)` so I can filter parents by a simple related column equality.
44. As a developer relating rows, I want `Select::with_count(relation) -> Select` so the parent gets a `relation_count` field.
45. As a developer relating rows, I want `Select::with_sum(relation, col)`, `with_avg`, `with_min`, `with_max`, `with_exists` so I get aggregates on the parent.
46. As a developer relating rows, I want `ModelCollection::load_count(relation)` so I can load counts on already-fetched models.
47. As a developer relating rows, I want nested `with` (e.g., `with(Author::POSTS, Post::COMMENTS)`) so I can eager-load deep trees.
48. As a developer relating rows, I want `Loaded::load(relation, closure)` so I can lazy-load a relation on a loaded set.
49. As a developer relating rows, I want `Loaded::load_missing(relation)` so I only load if not already loaded.
50. As a developer relating rows, I want `Include::constrain(closure)` so I can shape eager loads per type (for morphTo).

### The developer who scopes queries

51. As a developer scoping queries, I want parameterized scopes: `User::of_type(UserType::Admin)` so scopes can take arguments.
52. As a developer scoping queries, I want multiple global scopes via `#[rok(scoped_by = path::to::fn)]` repeatable so I can compose cross-cutting concerns.
53. As a developer scoping queries, I want `Select::prevent_lazy()` so missing `with` becomes an error in dev.

### The developer who controls serialization

54. As a developer controlling serialization, I want the generator to emit `UserDto` (all columns) and `UserPublicDto` (visible subset, no password) so I have a safe public shape.
55. As a developer controlling serialization, I want `UserWithExtrasDto { #[serde(flatten)] base: UserDto, is_admin: bool, ... }` for computed fields so accessors appear in JSON.
56. As a developer controlling serialization, I want per-field date format via `#[rok(cast(created_at = "datetime:Y-m-d"))]` so serialization format is declarative.
57. As a developer controlling serialization, I want global `#[rok(serialize_date = "format")]` so all dates use one format unless overridden.
58. As a developer controlling serialization, I want `ModelCollection::to_json()` so I can serialize a collection directly.

### The developer who casts attributes

59. As a developer casting attributes, I want `#[rok(casts(flag = "boolean"))]` so `i16`/`int` columns become `bool`.
60. As a developer casting attributes, I want `#[rok(casts(options = "json"))]` so `JSONB` columns become `serde_json::Value`.
61. As a developer casting attributes, I want `#[rok(casts(tags = "array"))]` so text arrays become `Vec<String>`.
62. As a developer casting attributes, I want `#[rok(casts(published_at = "datetime"))]` / `date` / `timestamp` so date columns use the right Rust type.
63. As a developer casting attributes, I want `#[rok(casts(secret = "encrypted"))]` so sensitive columns are encrypted at rest.
64. As a developer casting attributes, I want `#[rok(casts(status = MyEnum))]` so enum columns use the `DbEnum` type (already works).
65. As a developer casting attributes, I want `#[rok(cast(address = AsAddress))]` where `AsAddress` implements `Cast<Model>` with `get(&Model) -> Address` and `set(&mut Model, Address) -> Vec<(&str, Value)>` so multi-column value objects work.
66. As a developer casting attributes, I want `#[rok(cast(password = AsHash:sha256))]` with inbound-only cast so passwords are hashed on write only.
67. As a developer casting attributes, I want `#[rok(cast(address = Address))]` where `Address: Castable` so the value object provides its own caster.
68. As a developer casting attributes, I want cast parameters via `Type:param1,param2` syntax so casts are configurable.

### The developer who paginates

69. As a developer paginating, I want `Select::simple_paginate(page, per_page) -> SimplePage<T>` so I can paginate without a `COUNT(*)` query.
70. As a developer paginating, I want `Page::build_urls(base, page_param, extra, fragment) -> PageUrls` so the handler can return paginator-shaped JSON with links.
71. As a developer paginating, I want `Page<T>` and `CursorPage<T>` to serialize to the paginator JSON shape (`total`, `current_page`, `last_page`, `next_page_url`, `prev_page_url`, `data`, `next_cursor`, `prev_cursor`, `has_more`) so the generated API answers a familiar shape.
72. As a developer paginating, I want `CursorPage::prev` so I can show a "Previous" link in cursor pagination.
73. As a developer paginating, I want the generated handlers to return `PaginatedResponse<T>` / `CursorResponse<T>` with OpenAPI schemas so the API docs are accurate.
74. As a developer paginating, I want `cursor_paginate` to accept `page_name` for multiple paginators (handled in handler).

### The maintainer

75. As a maintainer, I want all new methods covered by the facade integration suite (SQL-shape + DB-backed) so regressions are caught.
76. As a maintainer, I want the generator's module fixtures to pin the new emitted code so drift is visible.
77. As a maintainer, I want the vertical slice `examples/api` to use the new surface so it stays the reference implementation.
78. As a maintainer, I want ADRs recorded for each decision cluster so future readers understand the trade-offs.

## Implementation Decisions

### D1 — Release strategy

- **0.4.0 is minor (additive)** — 0.3.0 was breaking; 0.4.0 only adds. No migration guide needed for 0.3.0 → 0.4.0.
- Work is split into **vertical slices** (tickets) each cutting through runtime, derive, generator, tests, docs.
- Each slice is independently testable and mergeable.

### D2 — Runtime surface additions

| Area | New items |
|------|-----------|
| `Model` trait (static) | `first_or_create`, `update_or_create`, `prevent_lazy_loading()` |
| `Model` trait (instance) | `fresh`, `replicate`, `increment`, `decrement`, `touch`, `update_or_insert` |
| `Select` chain | `where_any`, `where_all`, `where_none`, `where_json_contains`, `where_json_contains_key`, `where_json_length`, `where_date`, `where_month`, `where_day`, `where_year`, `where_time`, `where_column`, `where_null_safe_eq`, `union`, `union_all`, `increment_each`, `tap`, `pipe`, `debug`, `debug_raw`, `select_raw`, `where_raw`, `having_raw`, `order_by_raw`, `group_by_raw`, `simple_paginate`, `prevent_lazy` |
| `ModelCollection<M>` | `find`, `find_or_fail`, `model_keys`, `load`, `load_missing`, `unique`, `to_query`, `contains`, `partition`, `intersect`, `diff`, `except`, `only`, `fresh`, `to_json`, `Serialize` impl |
| `Page<T>` | `build_urls`, `Serialize` (paginator shape), `SimplePage<T>` (new type for `simple_paginate`) |
| `CursorPage<T>` | `prev: Option<Cursor>`, `Serialize` (cursor shape) |
| `HasMany`/`HasOne`/`BelongsTo` | `save`, `create`, `save_many`, `create_many`, `associate`, `dissociate` |
| `BelongsToMany` (new) | `attach`, `detach`, `sync`, `sync_without_detaching`, `toggle`, `update_existing_pivot` |
| `HasManyThrough`/`HasOneThrough` (new) | `query(&self) -> Select<Final>`, `load` |
| `Include` | nested `Vec<Include>`, `constrain(closure)` for morphTo |
| `Loaded` | `load(relation, closure)`, `load_missing(relation)` |

### D3 — Derive attribute grammar (additions)

| Attribute | Purpose |
|-----------|---------|
| `#[rok(scoped_by = "path::to::fn")]` (repeatable) | Multiple global scopes |
| `#[rok(scopes(name = "path::to::fn", ...))]` | Named scopes (supports parameters) |
| `#[rok(casts(field = "type", ...))]` | Standard casts: `boolean`, `json`, `array`, `datetime`/`date`/`timestamp` (with format), `encrypted`, `enum` |
| `#[rok(cast(field = AsCustomCast:param1,param2))]` | Custom cast (inbound-only if only `set`) |
| `#[rok(cast(field = ValueObject))]` where `ValueObject: Castable` | Value object with its own caster |
| `#[rok(has_many_through(name = Final::FK, through = Through::FK))]` | Has-many-through |
| `#[rok(has_one_through(name = Final::FK, through = Through::FK))]` | Has-one-through |
| `#[rok(belongs_to_many(target = Target, pivot = pivot_table))]` | Many-to-many |
| `#[rok(touches(relation))]` | Touch parent timestamps on child write |
| `#[rok(serialize_date = "format")]` | Global date serialization format |
| `#[rok(prunable = "path::to::fn")]` | Deferred — not in 0.4.0 |

### D4 — Generator emissions

- Generated models get all D3 attributes inferred from schema:
  - FK chains → `has_many_through` / `has_one_through`
  - Join tables (two FKs + unique) → `belongs_to_many` with `attach`/`detach`/`sync`/`toggle`
  - `BOOLEAN` → `boolean` cast, `JSONB` → `json`, `TIMESTAMPTZ` → `datetime`, `DATE` → `date`, `ENUM` → `enum`
  - `password` column → `encrypted` cast (if `pgcrypto` available) or `inbound` hash cast
- Generated DTOs: `UserDto` (all columns), `UserPublicDto` (no `password`/`secret`), `UserWithExtrasDto` (computed fields from accessors)
- Generated handlers return `PaginatedResponse<T>` / `CursorResponse<T>` with the paginator JSON shape
- OpenAPI: generic `PaginatedResponse<T>`, `CursorResponse<T>` schemas

### D5 — Testing seams (unchanged from 0.3.0)

1. **Facade integration suite** — hand-written models + DB, SQL-shape assertions
2. **Engine module-fixture corpus** — generated output expectations
3. **Compile fixtures + `examples/api`** — regenerate, compile, `rok gen check`

## Testing Decisions

- **Good test** = observable behavior: SQL string, returned row, error type. Not internal builder shape.
- **Facade suite** gets new test modules: `casts`, `scopes_params`, `relations_through`, `belongs_to_many`, `pagination_simple`, `query_sugar`, `serialization`.
- **Module fixtures** updated for: `belongs_to_many` pivot methods, `has_many_through`, `with_count`/`with_sum`, `simple_paginate`, `where_any`/`where_json`, `union`, `increment_each`, `tap`/`pipe`.
- **DB-backed tests** use `DATABASE_URL`; skip with printed note when unset (existing behavior).
- **No new seams** — all testing through existing three seams.

## Out of Scope

- **Full JSON:API** (sparse fieldsets, includes parsing, compound documents) — defer to 0.5.0
- **Polymorphic relationships** (`morphTo`, `morphOne`, `morphMany`, `morphToMany`) — defer to 0.5.0
- **Custom pivot models** (`using(RoleUser::class)`) — defer
- **Chaperone** (auto-hydrate parent on child) — defer
- **Default models on `belongs_to`** (`withDefault`) — not idiomatic Rust
- **Prunable / MassPrunable** — needs scheduler (`rok serve`)
- **Observer/Event system** (`creating`, `created`, `ObservedBy`, `withoutEvents`, `saveQuietly`) — defer
- **Custom cast serialization** (`SerializesCastableAttributes`) — defer
- **Query-time casting** (`withCasts`) — defer
- **Accessor caching** — not idiomatic Rust
- **Bootstrap/Tailwind pagination views** — not a server-rendered framework

## Further Notes

### Deliberate differences from dynamic ORMs

- **No `fillable`/`guarded`** — typed DTOs (`NewUser`/`UpdateUser`) are the compile-time allow-list.
- **No dynamic properties** — relations are explicit method calls (`user.posts()`), not magic `__get`.
- **No `save` ambiguity** — instance verbs are `insert` / `update` / `upsert` (0.3.0 decision).
- **`where` is `filter` / `where_`** — Rust keyword; `where_` alias provided.
- **Collections are `ModelCollection<M>` with `Deref<Target=Vec<M>>`** — not a separate `Collection` class with 100+ methods. We add the 15 high-value ones.
- **Serialization is DTO-based** — no `Hidden`/`Visible`/`Appends` on the model; DTO variants handle it.
