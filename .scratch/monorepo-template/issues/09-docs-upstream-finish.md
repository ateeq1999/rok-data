- `rok init --template monorepo` printed a single crate's next steps; it now prints the engine's `Scaffolded::template_next_steps`, as `rok sqlc init` does (both now name `clients/rust`). Test: `tests/init.rs::init_monorepo_prints_the_apps_next_steps`.
- `rok gen --migration <name>` from a monorepo's root staged the api's pair in the root's `migrations/`, as a first migration of the whole schema (the App's unset `migrations` fell back to a cwd-relative default). It now lands in `apps/api/migrations/` (`0009_add_bio`, one `ALTER TABLE ... ADD COLUMN`). Test: `tests/gen.rs::gen_stages_an_apps_migration_in_the_apps_history_dir` (red first).
- `rok init --help` said `--schema` seeds `migrations/`; it seeds `schema/`.
- ADR 0027 says `template_drift` keeps `apps/api` equal to the axum template, but nothing compared them and two doc comments had drifted; synced, and `template_drift` now checks it (red first on the drifted copy).

**Found, not fixed (for a follow-up ticket).** The api has three schemas named `UserResponse` (`features/users`, `account`, `auth`); utoipa registers one component under that name. While all three have the same fields nothing shows, but after adding a `bio` column the generated users DTO gains `bio` while the component (`GET /users/{id}`'s documented answer) does not, and the paginated list's inline items do: the Rust client then types `users().get_one` and the list items differently, and `tests/client/admin.rs` stops compiling. The contract under-describes what the API answers.
