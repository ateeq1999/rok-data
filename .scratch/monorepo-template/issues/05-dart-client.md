# 05: Generated Dart Client

**What to build:** `clients/dart`: a typed pub package emitted from the same `openapi.json` reader, shaped for the mobile ticket that will consume it (06): typed calls for every path, models for the schemas, session credential handling consistent with the api's auth (bearer/cookie as the spec defines), and the same error surface per operation (validation issues surfaced, not swallowed). A fresh scaffold gains `clients/dart` at init; `rok gen` regenerates it with the api artifact; generated-marker rules apply. Verifiable standalone: emission is unit-tested against the api's spec, and the emitted package itself passes its own static analysis where a toolchain exists (this ticket does not bring the Flutter app — that is 06).

**Blocked by:** 04 (OpenAPI artifact + the subset model the readers share).

**Status:** done

- [x] Emission covers the whole utoipa subset the api's spec exercises: paths, methods, schemas/oneOf where emitted, request/response bodies, statuses; unsupported constructs are reported, not invented
- [x] The emitted package is idiomatic enough for a Flutter consumer: one client class with typed methods, model classes, a session credential provider hook, one consistent error type carrying status + validation issues
- [x] Init emits `clients/dart`; `rok gen` regenerates it after re-exporting the api artifact; generated markers carry on the files so re-emission policy matches the other Clients
- [x] Emission is snapshot/round-trip tested: regenerating from the same spec is stable; changing the spec changes the client in the expected places
- [x] The emitted package passes static analysis when the toolchain is present (skip-with-note otherwise), so ticket 06 starts from a sound package; format/clippy and all Rust suites green

## Comments

**Where things live.** `clients::dart` in the engine, beside `clients::ts`, reading the same `clients::openapi` model and reusing the TS emitter's operation naming (`ts::name_operations`), so `api.auth.verify2fa` is the same name in both. `[clients]` takes `dart = "clients/dart"`; the monorepo's `rok.toml` names it, so `init --template monorepo` emits it and `rok gen`/`rok gen check` keep it, with the writer rules the TS client has. The template's checked-in `clients/dart` refreshes only through the `ROK_DATA_SQLC_UPDATE_EXPECTED=1` run of `fixture_compile/monorepo_template.rs`. Engine ADR 0027 records the shape.

**The package** (`api_client`, depends on `http` only): `ApiClient(baseUrl:, session:, httpClient:)`; a getter per tag and a method per operation (path parameters and body positional, query parameters named, `options` last); a `final class` per object schema with `fromJson`/`toJson`, an `enum` per string enum, a `sealed class` per `oneOf` of objects (`LoginResponse` = `TokenResponse | LoginResponsePendingToken`, told apart by required keys); `Session` (`token()`, `expired(token)`) as the credential hook; `ApiException` (`status`, `code`, `message`, `details` of `FieldIssue`s, `issuesOf(field)`) for every failure, including no answer (status 0) and an unreadable success (`invalid_response`).

**Markers.** Dart files carry `// @generated`; `pubspec.yaml`, `analysis_options.yaml` and `.gitignore` carry `# @generated by rok-data-sqlc ...`. The writer's marker check now accepts that `#` form (and its legacy `rok-sqlc` words), so those files follow the same rewrite/refuse/stale rules; Cargo's own `@generated` lock line does not match.

**Gate.** `crates/rok-cli/tests/fixture_compile/dart_client.rs` scaffolds the monorepo, copies `dart_client_test.dart` (six tests over `package:http/testing.dart`'s `MockClient`: a public call sends no token and reads a `oneOf` variant; a secured call sends the bearer token, encodes the path and sends a cleared field as `null`; query wire names; a `422`'s field issues; a `401` ends the session unless `keepSession`; no answer is status 0) into `clients/dart/test/`, then runs `dart pub get` (falling back to `--offline`), `dart analyze --fatal-infos` and `dart test`. It skips with a note only when `dart` (or Flutter's `dart.bat` on Windows) does not run.

**Judgement calls.** A request schema's optional, nullable field is `Nullable<T>?` (left out keeps, `Nullable(null)` clears), because the api's `PATCH` DTOs are `Option<Option<T>>`; only schemas no response reaches get it, so responses read as plain `T?`. The emitted Dart is laid out close to `dart format` but is not run through it: the gate holds it to the analyzer, not the formatter. Models carry no `==`/`copyWith`; ticket 06 should not rely on value equality without adding it. Tests went red first for the file set and the `#` marker; the rest of the emitter's tests were written right after its first cut.
