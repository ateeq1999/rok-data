# 06: Mobile App imported and ported — apps/mobile on the monorepo contract

**What to build:** The Flutter starter (`ateeq1999/Nestjs-Better-Auth-Flutter-Starter`) is imported as the monorepo's `mobile` App and its data layer is ported to the monorepo backend's contract **through the generated Dart client** (05) — its NestJS/Better-Auth client code is gone, and the app talks to `apps/api`. Surfaces the backend doesn't serve yet (organizations, magic link, admin, delete account) are hidden, not half-dead; push notifications stay out as a written recipe decision (FCM, ADR 0023). Firebase configuration ships as a placeholder (it is tied to one Firebase project) plus the recipe to make it real. Init writes `apps/mobile`; the app runs against the local api (sign in, core screens); it is gated like the rest: `flutter analyze`, `flutter test` from `fixture_compile/`, skip-with-note without the toolchain, CI installs it.

**Blocked by:** 05 (generated Dart Client — the port's data layer).

**Status:** done

- [x] `apps/mobile` is vendored (single source of truth — upstream archived later, ticket 09) and init writes it like the other Apps: files-if-absent across the whole monorepo, embedding with no stray platform build output or secrets (real `google-services.json`/Firebase values can never ship; the placeholder does)
- [x] The data layer is generated-client-only: HTTP calls, models and error handling come from `clients/dart`; hand-written NestJS-era api code is removed; auth/session logic cards through the generated client against the api's actual endpoints
- [x] Unservable features are hidden: navigation/entries for organizations, magic link, admin and delete-account point nowhere or are absent, each with a note of the backend gap, so the app remains browsable and honest
- [x] Firebase placeholder + recipe; screenshots/tests updated to the local contract; `flutter analyze` and `flutter test` pass on the scaffolded app (live locally against `apps/api`)
- [x] Gate: fixture_compile test runs the flutter gates with skip-with-note when the toolchain is absent; CI installs the toolchain; format/clippy and all Rust suites stay green

## Comments

**Import.** `ateeq1999/Nestjs-Better-Auth-Flutter-Starter` at `13e2139` (`13e21398dc53bd09d0ad08310778177412509e43`), vendored at `crates/rok-templates/templates/monorepo/apps/mobile/`. Mechanical alignment only: the pub package is named `mobile` (its App in the catalog, `MONOREPO_APPS`) and the tests import it so; the upstream repository's `.github/`, `CHANGELOG.md`, `CONTRIBUTING.md` and `LICENSE` are not an App's files and are not shipped. The starter checked in a real Firebase project's configuration (`google-services.json`, `GoogleService-Info.plist`, `firebase_options.dart`, `firebase.json`): each was replaced by a placeholder for `your-firebase-project` before the first commit, so no real value is in the history. The imported tree did not pass its own gates (`flutter analyze`: two `String?` errors in the organizations routes and a missing `.env` asset; `flutter test`: "No file or variants found for asset: .env"), so the flutter gate arrived with the port.

**Embedding.** `build.rs`, `Cargo.toml`'s `include` and the lib tests leave out what resolving or building a Flutter App in place writes: `.dart_tool/`, `build/`, `ephemeral/`, `.gradle/`, `.kotlin/`, `.cxx/`, `Pods/`, `.symlinks/`, `.pub-cache/`; `.flutter-plugins(-dependencies)`, `local.properties`, `key.properties`, `Generated.xcconfig`, `flutter_export_environment.sh`, the Gradle wrapper, the Android/iOS `GeneratedPluginRegistrant.{java,h,m}`; `*.jks`/`*.keystore`. Checked red with them present in the template (`tests/package.rs`'s exact-match test then confirms the package agrees). `rok-templates-0.5.0.crate` is 1,483,783 bytes (5.3 MiB unpacked, 1225 files).

**The port.** `api_client` is a path dependency (`../../clients/dart`); Dio, `flutter_dotenv`, the providers, models, `response_parser` and `ApiException` of the starter are gone. `AuthService` implements the client's `Session` (token in secure storage; `expired` signs out when the rejected token is still the session's). `AuthRepository`/`UserRepository` are thin uses of `api.auth.*`, `api.users.*`, `api.avatars.*`; failures are the client's `ApiException`, and forms read a `422`'s issues through the `fieldErrors` extension (`core/errors/field_errors.dart`). Sign-in follows the API's `LoginResponse`: a `TokenResponse` is saved, then `auth.me` reads the user (the starter never persisted the sign-in token); a `LoginResponsePendingToken` goes to `/two-factor` as the route's `extra`. Two-factor maps onto `setup` → `enable(code)` (recovery codes shown once) → `disable(password)`, all with `keepSession`. Settings are `--dart-define`s (`--dart-define-from-file=.env` reads `.env.example`'s format), `API_URL` defaulting to `127.0.0.1:8080`, `10.0.2.2:8080` on Android.

**Hidden features** (no routes, entries or code; no API routes invented; each noted in `apps/mobile/docs/feature-flags.md`):

- Organizations (list, detail, members, invite, accept-invitation deep link): `apps/api` has no organization endpoint.
- Magic-link sign-in (the sign-in button, `/magic-link`, its deep link): no magic-link endpoint.
- Admin panel (dashboard stats, users, user detail, audit logs): the stats and the per-user actions it used are not served; `users.list` and `auditLog.list` exist, so a reduced panel can return through the client.
- Delete account: no self-service delete (`DELETE /users/{id}` is an admin's).
- OAuth sign-in (the `auth/callback` deep link and its flag): no OAuth endpoints.
- Push notifications (FCM init, device-token registration, `firebase_*`, `flutter_local_notifications`): no device-token endpoint, and push picks a vendor — `apps/mobile/docs/push-notifications.md` is the recipe (placeholder → `flutterfire configure` → token → an `apps/api` endpoint through `rok gen`). The FlutterFire Gradle plugin is no longer applied, so the placeholders are not read.
- Server-side sign-out: the API has none; signing out forgets the token on the device.
- The sign-up "Full Name" field: `auth.register` takes email and password; the display name is set from the profile.
- "Resend verification email" on the verify screen: `auth.resend` is secured (a signed-in user only), so it moved to the profile's email row.

**Tests** (67 upstream → 45): removed with their features `admin_repository_test`, `organization_repository_test`, `magic_link_cubit_test`; `api_exception_test` and `auth_repository_signin_test` tested the removed Dio error parsing and provider. New: `auth_repository_test` and `user_repository_test` (the real client over `MockClient`: bodies, paths, bearer header, the `oneOf` answer, a `422`'s field issues, `keepSession`), `session_test` (a `401` signs out only the matching token), `field_errors_test`, cubit tests for the two-factor step; the bloc and widget tests use the generated `UserResponse`. `integration_test/` compiles (the analyzer covers it) but is not run by the gate, as upstream.

**Live check** (not committed): a scaffold's `apps/api` (after `rok gen`) on a throwaway PostgreSQL, and a throwaway `flutter test` driving the App's repositories over a real `http.Client`: a bad sign-up answered `422 validation_failed` with both field issues; sign-up; a made-up verification token `400 invalid_token`; sign-in before verification `403` (`REQUIRE_VERIFIED_EMAIL=true`); with the email marked verified in the database (`MAIL_TRANSPORT=log` logs no body, so the mailed token was not readable), sign-in saved the token, `updateMe` set the display name, `auth.setup` answered an `otpauth://` URI, a wrong first code kept the session, changing the password ended it, the old token was refused `401`, and the new password signed in. The screens themselves were not driven on a device or emulator.

**Judgement calls.** Hidden features are removed rather than flagged off (as the web port did); their former flags are gone. The upstream's unused dependencies outside the data layer (`equatable`, `flutter_form_builder`, `form_builder_validators`, `intl`, `hydrated_bloc` storage, `flutter_windowmanager` 0.2.0) are kept as imported; the codegen ones (`freezed`, `json_*`, `build_runner`) went with the hand-written models. Platform ids (`com.example.flutter_starter`, display name "Flutter Starter") are left for ticket 08's renames. The FCM recipe lives in the App's `docs/`; ticket 09 can move it into the templates' guide. The `mobile` CI job pins `subosito/flutter-action@v2` with Flutter 3.47.1.

**Gates** (after merging the integration tip with ticket 07): `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test -p rok-templates`, `cargo test -p rok-data-cli --test init` and the mobile fixture (2 passed, ran with Flutter 3.47.1; without Flutter on `PATH` it prints its skip note) are green. The workspace run (`--skip desktop_app --skip mobile_app`, `--no-fail-fast`) passed except two failures this ticket does not touch: `fixture_compile::api_app::api_app_generated_code_is_rustfmt_clean` ("The filename or extension is too long", os error 206: the rustfmt command line over the long worktree path on Windows), and `rok-data-core`'s criterion bench `builder`, which rejects `--skip` (it does with the existing single `--skip desktop_app` as well).
